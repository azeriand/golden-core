# Requirements Document: Media Transcoding & Original Preservation

## Introduction

Today the app compresses images **client-side** before upload (`lib/image-preprocess.ts`) and stores only that reduced version in Vercel Blob; videos are uploaded **raw** (up to a 100 MB cap) and served uncompressed. There is a working Railway `Poster_Worker` that generates a poster frame for each video (`worker/`, `poster_jobs` queue).

This feature changes the storage-and-delivery model to an **"originals archive + optimized delivery"** model:

- The **original** file (full-quality photo/video) is always preserved in Blob for future high-quality delivery (e.g. WeTransfer batch download). It is never what the gallery serves.
- A **display derivative** (reduced image / transcoded video) is generated **server-side on the worker** and is what the app shows in the masonry grid and the full-screen preview/playback.
- While a derivative is not yet ready, the app shows the **original** as a graceful fallback, then swaps to the derivative when it lands (mirroring the existing poster placeholder → poster swap in `media-item.tsx`).
- The client stops pre-compressing images; it uploads originals.
- The 100 MB cap is **raised to an exaggerated guardrail** (system-overload protection only, not a quality gate), because any modern phone video can exceed 100 MB.

The existing poster generation, idempotency conventions (`upload_id` / `ON CONFLICT`), direct-to-Blob upload handshake, and secret-handling rules are preserved and extended, not replaced.

## Glossary

- **Original**: the untouched bytes the user uploaded (full-quality). Preserved for future WeTransfer-style delivery. Never transcoded/re-encoded.
- **Display derivative** (or just **derivative**): the reduced/transcoded version generated by the worker and served by the app. For images: a downscaled, re-encoded image. For videos: a transcoded, bitrate/resolution-capped video.
- **Poster**: the existing single still frame for a video (unchanged behavior; complements the video derivative).
- **Job**: a row in the worker's Postgres-backed queue describing work to do for one media row.

---

## Requirement 1: Preserve the original for every upload

**User Story:** As the event owner, I want every uploaded original preserved at full quality, so that I can later deliver the best-quality media to guests (e.g. via WeTransfer) without re-collecting anything.

#### Acceptance Criteria

1. WHEN a photo or video is uploaded THEN the system SHALL store the original bytes in Vercel Blob without any server-side or client-side re-encoding of the original.
2. WHEN the original is stored THEN the system SHALL persist a reference to the original's Blob URL on the media row in a dedicated column that is distinct from the column the app serves.
3. The system SHALL NOT delete the original when a derivative is generated.
4. IF derivative generation fails permanently THEN the original SHALL remain available and the app SHALL continue to serve the original.
5. The original-URL column SHALL be additive and nullable so all existing (legacy) media rows remain valid; a NULL original reference on a legacy row SHALL be interpreted as "the served `content` is the only version".

## Requirement 2: Stop client-side image compression; upload originals

**User Story:** As a guest, I want my full-quality photo preserved, so that the couple can later get the original, not a downscaled copy.

#### Acceptance Criteria

1. WHEN a guest selects an image to upload THEN the client SHALL upload the original image bytes (no canvas downscale/re-encode of the uploaded bytes).
2. The client SHALL continue to compute a BlurHash and, where possible, intrinsic width/height for placeholder/layout purposes WITHOUT altering the uploaded original bytes.
3. IF measuring dimensions or computing a BlurHash fails THEN the upload SHALL proceed unaffected (non-blocking, matching current behavior).
4. The change SHALL NOT remove the client's existing upload reliability features (concurrency cap, retries, IndexedDB-persisted resume, idempotent `upload_id`).

## Requirement 3: Worker-side image display derivative

**User Story:** As a guest browsing the gallery, I want images to load fast and cheap, so that scrolling is smooth and the couple's bandwidth cost stays low.

#### Acceptance Criteria

1. WHEN an image media row is created THEN the system SHALL enqueue a job to generate an image display derivative.
2. WHEN the worker processes an image derivative job THEN it SHALL produce a downscaled, re-encoded image capped at a configurable maximum dimension and upload it to Blob under a deterministic, media-namespaced path.
3. WHEN the derivative upload succeeds THEN the worker SHALL record the derivative's Blob URL as the media row's served `content` (the app then serves the derivative), while the original reference remains untouched.
4. The worker SHALL use the already-present `sharp` dependency for image derivatives (no new image dependency).
5. IF the derivative would not be smaller than the original THEN the worker MAY keep serving the original (never enlarge / never bloat), and SHALL still mark the job complete.
6. Image derivative generation SHALL be idempotent: a re-run for an already-derived row SHALL NOT duplicate work or corrupt the served `content`.

## Requirement 4: Worker-side video transcode

**User Story:** As the event owner, I want videos served in a normalized, reduced form, so that playback is smooth for guests and egress cost is controlled, while the original stays archived.

#### Acceptance Criteria

1. WHEN a video media row is created THEN the system SHALL enqueue a job to transcode a video display derivative (in addition to the existing poster job, or as part of a unified video job).
2. WHEN the worker processes a video transcode job THEN it SHALL produce a transcoded video capped at a configurable maximum resolution and target bitrate/codec (e.g. H.264 1080p) using the ffmpeg binary already provided by the worker image, and upload it to Blob under a deterministic, media-namespaced path.
3. WHEN the transcode upload succeeds THEN the worker SHALL record the transcoded derivative's Blob URL as the media row's served `content`, while the original reference remains untouched.
4. The system SHALL preserve existing poster generation behavior for videos (the poster still complements the video, and video playback uses `preload="none"`).
5. IF transcoding fails permanently (after retries) THEN the app SHALL continue to serve the original video (the original remains the fallback), and the failure SHALL NOT crash the worker or stall other jobs.
6. Video transcode SHALL be idempotent: a re-run for an already-transcoded row SHALL NOT regenerate or corrupt the served `content`.

## Requirement 5: Job model supporting multiple job kinds

**User Story:** As a maintainer, I want the worker queue to cleanly support poster, image-derivative, and video-transcode work, so that the pipeline stays understandable and each kind retries independently.

#### Acceptance Criteria

1. The queue SHALL represent the distinct kinds of work (poster, image derivative, video transcode) such that each kind for a given media row is enqueued at most once (idempotent enqueue via a unique constraint, mirroring the existing `poster_jobs.media_id` + `ON CONFLICT DO NOTHING` pattern).
2. WHEN enqueue is attempted more than once for the same media row and kind THEN exactly one job SHALL exist for that (media row, kind).
3. Each job kind SHALL retry and back off independently using the existing attempts/backoff/Max_Attempts machinery.
4. A failure of one kind SHALL NOT prevent another kind from succeeding for the same media row (e.g. a failed transcode SHALL NOT block the poster).
5. The schema change SHALL be additive and reversible and SHALL keep existing poster jobs working (existing rows migrate cleanly to the extended model).

## Requirement 6: Gallery serves derivative, falls back to original

**User Story:** As a guest, I want media to appear immediately even before its optimized version is ready, so that the gallery never shows empty slots.

#### Acceptance Criteria

1. The event data API SHALL expose, per media item, the served URL (`content`) and enough information for the client to render an immediate view while a derivative is pending.
2. WHEN a media item's derivative is not yet ready THEN the app SHALL display the original as the fallback (for images: the original image; for videos: the existing poster placeholder + `preload="none"` original playback).
3. WHEN a derivative becomes available (on subsequent loads) THEN the app SHALL serve the derivative as `content`.
4. The gallery SHALL continue to use `next/image` for images on top of whatever `content` is (derivative or original), preserving lazy loading, blurhash placeholders, and reserved aspect ratios.
5. The full-screen preview/zoom and video playback SHALL use the served `content` (derivative when ready, original otherwise).

## Requirement 7: Raise the upload size cap to an overload guardrail

**User Story:** As the event owner, I want normal phone videos to upload successfully, so that guests are not blocked, while still protecting the system from absurdly large files.

#### Acceptance Criteria

1. The system SHALL raise `MAX_FILE_SIZE` from 100 MB to an exaggerated guardrail value (system-overload protection only), applied consistently across every enforcement point (client preprocessing/validation, upload-token handshake `maximumSizeInBytes`, and the confirm route).
2. The three enforcement points SHALL agree on the same limit (no divergence).
3. WHEN a file exceeds the guardrail THEN the client SHALL surface a clear, user-facing message explaining the limit (not a silent failure).
4. The cap change SHALL NOT weaken any existing content-type validation.

## Requirement 8: Preserve secret handling and reliability conventions

**User Story:** As a maintainer, I want the existing security and reliability guarantees kept, so that this feature does not regress the codebase's standards.

#### Acceptance Criteria

1. `BLOB_READ_WRITE_TOKEN` and `DATABASE_URL` SHALL remain server/worker-side only; they SHALL never be returned to the client or logged.
2. Media-row creation SHALL remain idempotent via the existing `upload_id` unique index and `ON CONFLICT DO NOTHING`.
3. The worker SHALL preserve bounded concurrency, retry/backoff, stale-processing reclaim, and secret-free structured logging.
4. WHEN the worker writes the served `content` to a derivative THEN it SHALL write the single final URL only after a successful upload (never a partial value), scoped to the one media row.
5. All schema changes SHALL be additive and reversible, following the numbered-migration convention (`006_...`).

## Requirement 9: Backward compatibility and migration of existing media

**User Story:** As the event owner, I want media already uploaded to keep working, so that nothing breaks when this ships.

#### Acceptance Criteria

1. Legacy media rows (no original reference, no derivative) SHALL continue to render by serving their existing `content`.
2. The system SHALL provide (or extend the existing) idempotent backfill to enqueue derivative/transcode jobs for existing media where desired, without duplicating jobs.
3. The migration SHALL NOT modify or destroy existing `content` values for legacy rows.
4. IF a legacy video already has a poster THEN existing poster behavior SHALL be unaffected by the new job kinds.
